Signal Composition Bible

SQL-Metrics Studio Reference Complete guide to composing Signals from wide and tall metric tables

A Signal is a comparative metric watched over time. This document is the authoritative reference for how Signals are defined, how the engine builds them from any table shape, what the output must look like, and how Signals compose into Findings.

Everything here applies to the current project (wide region_metrics) and to any future table that follows either the wide or tall pattern.

1 — What is a Signal?

The five-tier model adds exactly one thing per tier:

Metric
→
a raw sum or level — no comparison, no reference: sales_eur = €4.2M
Comparative metric
→
…vs a reference: mshare_deviation = −2.76pp (region share − national average)
Signal
→
…watched over time: that deviation across 4 months — [−0.87, −1.63, −2.40, −2.76]
Finding
→
…composed with other signals: share + growth quadrant
Insight
→
…surfaced to a specific person with context
The Signal tier adds exactly one thing: a time window. It takes a comparative metric and builds its trajectory using LAG window functions. The trajectory is what makes a number meaningful — −2.76pp and falling for 3 months straight is a very different signal from −2.76pp stable.

2 — The Signal Contract (output shape)

Regardless of the source table, signal definition, or how the SQL is built, every signal computation must produce rows with this exact shape:

This shape is the contract. Whether the source table is wide or tall, whether it holds pharma data or hospital data, the engine always produces this shape. Every downstream consumer — Finding engine, Insight Framer, catalog writer — depends only on this shape.

3 — Signal Definition (the config)

A Signal Definition is a JSON object stored in studio.db. It fully describes how to compute the signal — no schema assumptions are baked into the engine code. All of these fields drive SQL generation.

JSON{
  "id":               "sig_mshare_dev_mat",
  "name":             "mshare_dev_mat_step_1m_3m",
  "label":            "Market Share Deviation (MAT, −1m/−3m)",

  // ── SOURCE: where to read from ────────────────────────────────
  "source_table":     "region_metrics",   // any table in metrics.db
  "entity_dimension": "region_name",      // PARTITION BY this column
  "time_dimension":   "year_month",       // ORDER BY this column

  // ── FILTERS: fixed WHERE conditions (AND-ed) ─────────────────
  "filters": [
    { "column": "period_type", "operator": "=", "value": "MAT" }
  ],

  // ── SEGMENT BY: run once per distinct value of these columns ──
  "segment_by": ["brand_name"],  // e.g. once per brand

  // ── METRIC: which numeric column to track over time ───────────
  "metric":           "mshare_deviation",

  // ── LAGS: how far back to look (0 = now) ──────────────────────
  "lags":             [0, 1, 2, 3],   // 4-point series: now, -1m, -2m, -3m

  // ── DELTA LAGS: which step-deltas to compute ─────────────────
  "delta_lags":       [1, 3],          // now−1m, now−3m

  // ── STRENGTH interpretation ────────────────────────────────────
  "direction":        "higher_is_better",
  "strength_kind":    "position",       // position = pp-scale; growth = %-scale
  "loud_threshold":   2.0              // V ≥ 2.0pp → "loud" severity bonus
}
Every field is a runtime parameter. Change source_table to "hospitals", entity_dimension to "hospital_id", metric to "readmission_rate" — and the identical engine produces hospital-level readmission signals. No code changes.

Signal definition (wide)

JSON{
  "source_table":     "region_metrics",
  "entity_dimension": "region_name",
  "time_dimension":   "year_month",
  "metric":           "mshare_deviation",   ← the column name IS the metric identifier
  "filters": [
    { "column": "period_type", "operator": "=", "value": "MAT" }

  "segment_by":  ["brand_name"],
  "lags":        [0, 1, 2, 3],
  "delta_lags":  [1, 3]
}

Generated SQL (wide)

The engine builds this SQL from the definition at runtime. No column name is hardcoded in engine code.

SQLWITH s AS (
  SELECT
    region_name  AS _entity,    -- entity_dimension
    year_month   AS _time,      -- time_dimension
    mshare_deviation             AS v0,   -- metric, lag 0 = now
    LAG(mshare_deviation, 1) OVER w AS v1,
    LAG(mshare_deviation, 2) OVER w AS v2,
    LAG(mshare_deviation, 3) OVER w AS v3
  FROM region_metrics
  WHERE period_type = 'MAT'           -- from filters[]
    AND brand_name =  'Oncleris'      -- from segment_by value (preview execution)
  WINDOW w AS (PARTITION BY region_name ORDER BY year_month)
)
SELECT * FROM s
WHERE _time = '2026-05'             -- asof
  AND v3 IS NOT NULL               -- enough history for maxLag=3

Raw query output for BE Burgdorf:

_entity_timev0 (now)v1 (−1m)v2 (−2m)v3 (−3m)
BE Burgdorf 2026-05 -2.76 -2.40 -1.63 -0.87

Output signal row (wide)

The engine reverses v3→v0 into series (oldest→now), computes deltas, and derives strength:

Output{
  "entity":   "BE Burgdorf",
  "series":   [-0.87, -1.63, -2.40, -2.76],   ← oldest → now
  "now":      -2.76,
  "deltas": {
    "delta_1m": -0.36,    ← v0 − v1  =  −2.76 − (−2.40)
    "delta_3m": -1.89     ← v0 − v3  =  −2.76 − (−0.87)
  },
  "strength": {
    "magnitude": 1.89,    ← |−0.76| + |−0.77| + |−0.36| = 1.89
    "net":       -1.89,    ← −2.76 − (−0.87) = −1.89
    "coherence": -1.00,    ← D/V = −1.89 / 1.89 = −1.0 (perfectly directional)
    "shape":    "trend"    ← |ρ| ≥ 0.8
  }
}

Generated SQL (tall)

The engine generates structurally identical SQL. The only differences are the table name and the extra filter condition on metric_type:

SQLWITH s AS (
  SELECT
    region_name  AS _entity,
    year_month   AS _time,
    value                      AS v0,   -- "value" column in tall format
    LAG(value, 1) OVER w AS v1,
    LAG(value, 2) OVER w AS v2,
    LAG(value, 3) OVER w AS v3
  FROM region_metrics_tall
  WHERE period_type  = 'MAT'
    AND metric_type  = 'mshare_deviation'  ← filter instead of column name
    AND brand_name   = 'Oncleris'
  WINDOW w AS (PARTITION BY region_name ORDER BY year_month)
)
SELECT * FROM s
WHERE _time = '2026-05'
  AND v3 IS NOT NULL

Key insight

In tall format, the metric identifier moves from a column selector to a filter value. metric: "mshare_deviation" (wide) becomes metric: "value" + filter: metric_type = 'mshare_deviation' (tall). The SQL engine doesn't know or care — it builds a LAG(value, N) expression either way.

Signal Strength — Formula

Strength is computed from series (always a pure number array, independent of table shape). Three measures — keep all three. None alone tells the full story.

V = Σ|δᵢ| where δᵢ = series[i] − series[i-1] // magnitude: total path length, always ≥ 0
D = series[last] − series[0] // net displacement: signed, direction of change
ρ = D / V if V > 0, else 0 // coherence ∈ [−1, +1]: how directional the move is

Why you need all three

ScenarioSeriesVDρWhat it means
Straight decline[-1, -2, -3, -4]3-3-1.0trend Every step same direction
Oscillating ±10[-10, +10, -10, +10]3000.0unstable V=30 but D=0 hides the volatility
Flat[2.1, 2.0, 2.1, 2.0]0.3-0.1-0.33quiet Below magnitude threshold
Mostly down, one bounce[-1, -2, +0.5, -3]4.5-2-0.44mixed Directional but not clean

Shape archetypes

trend

|ρ| ≥ 0.8 — strong directional coherence. Every step the same way. Most alarming when deteriorating.

unstable

|ρ| ≤ 0.2 and V is large. High noise, no net movement. Warrants monitoring but not a trend call.

mixed

0.2 < |ρ| < 0.8. Partial direction, some reversal. Most common real-world pattern.

quiet

V below the magnitude threshold (0.3 by default). The metric barely moved. Not worth surfacing as a finding.

Worked example — BE Burgdorf MS signal

Computationseries = [-0.87, -1.63, -2.40, -2.76]   ← oldest → now

step deltas:
  δ₁ = -1.63 - (-0.87) = -0.76   |δ₁| = 0.76
  δ₂ = -2.40 - (-1.63) = -0.77   |δ₂| = 0.77
  δ₃ = -2.76 - (-2.40) = -0.36   |δ₃| = 0.36

V = 0.76 + 0.77 + 0.36 = 1.89   (total path length)
D = -2.76 - (-0.87) = -1.89     (net displacement)
ρ = -1.89 / 1.89    = -1.00     (perfectly directional — every step the same way)

shape: |ρ| = 1.0 ≥ 0.8  →  "trend"

From Signal to Finding (N-D Composite)

A Finding composes N signals into one N-dimensional point. Every signal axis contributes its now (position), net (direction), and magnitude (loudness) to the composite. The quadrant (2-D) is the simplest case.

2-D: Share × Growth Quadrant

Two signals computed for the same entity at the same asof:

AxesAxis A — share position
  signal:  mshare_dev_mat_step_1m_3m
  now:     -2.76pp     ← below peers (bad side)
  ρ:       -1.00       ← deteriorating trend

Axis B — growth momentum
  signal:  growth_deviation_mat_step_1m_3m
  now:     -4.82pp     ← under-growing (bad side)
  ρ:       -1.00       ← deteriorating trend

Classification (both axes bad → losing_both):
  share   bad  (now < threshold = 0)  ✓
  growth  bad  (now < threshold = 0)  ✓
  → finding_key = "losing_both"

Per-axis severity scoring (each axis 0–3):

ConditionShare axisGrowth axis
+1 if below threshold (now < 0)+1 (−2.76 < 0)+1 (−4.82 < 0)
+1 if deteriorating (net < −delta)+1 (net=−1.89 < −0.3)+1 (net=−11.15 < −0.3)
+1 if loud (V ≥ loud_threshold)+1 (V=1.89 ≥ 2.0?) — borderline+1 (V=11.15 ≥ 10.0)
Axis severity3 / 33 / 3
Total severity score6 / 6 → band: critical

N-D generalisation

Stack any N signals. Strength lifts to N-dimensional space:

Concept1-D (single signal)N-D (composite finding)
MagnitudeV = Σ|δ|V = Σ‖step vector‖ (path length in N-space)
NetD = now − start (scalar)D = net displacement vector; ‖D‖ = loudness
Coherenceρ = D / Vρ = ‖D‖ / V (how directed the N-D move is)
"Bad" sidebelow thresholdbad orthant: every axis below its threshold
Composite loudnessper axisquiet drift on many axes, all the same way = loud composite
The most important consequence: A region can drift quietly on share, quietly on growth, and quietly on forecast-gap — each individually below the loud threshold — but all three drifting the same bad direction simultaneously is a loud composite. That signal is invisible to per-metric monitoring and surfaces only when you compose.

The generic engine — what it guarantees

The engine contains zero hardcoded:

  • Table names
  • Column names
  • Metric identifiers
  • Period types
  • Brand names or any segment values
  • Entity grain (region, hospital, product, country…)
  • Time grain (month, quarter, week…)

The complete parameterisation is in the Signal Definition JSON. Change the definition — the engine adapts. The output contract (the signal shape) never changes.

Wide: pharma regions
"source_table": "region_metrics"
"entity_dimension": "region_name"
"time_dimension": "year_month"
"metric": "mshare_deviation"
"filters": [{"column":"period_type","value":"MAT"}]
"segment_by": ["brand_name"]
Same engine: hospitals
"source_table": "hospital_metrics"
"entity_dimension": "hospital_id"
"time_dimension": "quarter"
"metric": "readmission_rate"
"filters": [{"column":"specialty","value":"cardiology"}]
"segment_by": ["region"]
